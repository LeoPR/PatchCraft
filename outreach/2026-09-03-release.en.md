# PatchCraft 0.5.1, news source

Dated document that feeds the channel texts in [`linkedin/`](linkedin/). Rule: no channel
text changes without this source changing first. Nothing here is an estimate; every number
has a command that reproduces it.

## What the library is

It cuts an image into patches and puts it back. One image per call, one tensor in and one
tensor out. There is no batch axis, no dataset, no dataloader and no model, and that
boundary is written as binding in `docs/THEORY.md` §0.

`pip install patchcraft` · MIT · pre-1.0 · Python 3.12 to 3.14 · torch 2.6 or newer.

## The headlines

### 1. The public retraction

The library stated, in its own docstrings and in fifteen places across the documentation,
when the round trip is bit-exact. The statement was wrong, and not by a little: it said the
error outside the rule stayed around 1 ULP, when it grows with the pixel's coverage count
and reaches 19 ULP in float32.

The correct contract, measured: the round trip is exact if and only if every value in the
coverage count map is a power of two. Outside that, the per-pixel error is bounded by
`(k+1)·eps·|v|`, with `k` that pixel's coverage count.

Why the suite never caught it is on the record too: the tests built their images with
`torch.arange`, and integer data round-trips exactly where random data does not.

### 2. The suite whose job is to bring the contract down

After the correction came a test whose explicit purpose is to falsify the new claim. It
enumerates the 126,736 legal geometries of the space independently of the predicate, draws
a seeded sample and tries to break both halves: it hunts for a case inside the predicate
that is not exact, and a case outside it that is exact by luck. The full sweep sits behind
`PATCHCRAFT_SWEEP_FULL=1`.

### 3. The two silent defects that motivate the library

The first is the reshape. `F.unfold` returns `(1, C*ph*pw, L)`, and the intuitive reshape
into `(L, C, ph, pw)` gives the right shape with the wrong pixels. Nothing complains.

The second is a stride that does not cover the image. On a 128 by 128 image with patch 32
and stride 20, the grid stops at pixel 112 and leaves 3840 of the 16384 pixels at zero. A
hand-rolled `fold` returns that partly black image without an error.

### 4. The native accelerator, and why the gain is not a core count

Five of the six wheels carry a Rust kernel for the overlapping fold, compiled into the
wheel itself. There is no extra to enable.

| Geometry | Call | Pure torch | Accelerated | Speedup |
|---|---|---|---|---|
| 3x512x512, patch 32, stride 16 | `reconstruct` | 16.3 ms | 2.3 ms | 7.1x |
| 3x2048x2048, patch 64, stride 32 | `reconstruct` | 453.7 ms | 32.1 ms | 14.1x |
| 3x2048x2048, patch 64, stride 32 | `stitch` hann | 460.9 ms | 37.9 ms | 12.2x |

The obvious objection is that the accelerator just uses more cores. It was measured:
forcing torch to 4, 8, 16 and 36 threads on the largest case, the pure path lands between
365 ms and 465 ms, and 36 threads is no better than 8. `F.fold` does not scale at batch
size 1, which is why the kernel exists.

The benchmark compares both paths with `torch.equal` before reporting any timing, and exits
non-zero if they differ.

## The state, in full

1534 tests pass, with CI on {Ubuntu, Windows} x {Python 3.12, 3.13, 3.14} on the pure path
plus an accelerated job on both systems. The public surface is 20 names, frozen by test
with `inspect.signature`.

No external project has consumed the library yet. No CUDA path in it has ever executed, in
CI or outside it. Three of the five accelerated wheels have never had their kernel run in
CI: the macOS and aarch64 ones are built and checked, and that is all.

## Reproduction

```
pip install patchcraft
python tools/benchmark.py --markdown
PATCHCRAFT_SWEEP_FULL=1 pytest tests/test_exactness.py
```
